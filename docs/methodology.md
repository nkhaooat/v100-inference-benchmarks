# Methodology and reproduction limits

## Hardware and campaign boundaries

The November 24–26, 2026 campaigns used a Ryzen 9 7945HX3D, 96 GiB installed RAM (approximately 93.5 GiB visible to Linux after iGPU/system reservations), and two V100 32 GB GPUs: one PCIe and one SXM2. Each GPU arm ran separately from production inference.

Launch limits varied: the initial Lapilli trials explicitly set an 80 GiB hard limit; the DeepSeek comparison used 78/82 GiB soft/hard limits; later sFNX, Q8 comparison and cache arms used 82/86 GiB. Storage placement also varied. The [report](reports/2026-11-26-v100-comparison.md) records those differences. The historical test settings are not a recommendation to raise limits on another machine.

## Quality accounting

Each full arm executed 974 trials, of which 966 were graded and eight were observation-only. The graded groups were local tasks (400), HumanEval (328), long context (6), concurrency (16), and tools/protocol (216). Trials repeat tasks across seeds, modes and concurrency settings; 966 trials are not 966 independent questions.

Reported passes retain the original grading contracts. Capped generations and strict-format/parser failures remain failures. A parser replay is not a regrade of an entire workflow, especially when later turns were never executed. No repeated full-suite runs establish run-to-run variance or statistical equivalence.

The tools suite primarily stresses XML protocol handling. It mixes generation, serving extraction, serialization and final-format behavior. Flash-Next and DeepSeek use different native protocols and sampling settings, so their aggregate tool scores are not a controlled comparison of general agentic capability.

## Timing definitions

- **Client TTFT:** elapsed time from request start to the first nonempty content or reasoning delta. It includes queueing, tokenization, prefill and transport overhead.
- **Streamed decode rate:** `(completion_tokens - 1) / (last content/reasoning delta time - first delta time)`. This is a client-side approximation; it is reported separately from engine decode counters.
- **Two-client aggregate throughput:** sum of completion tokens across the concurrent `code1` and `prose2` pair divided by the pair's total wall time, including prefill and queueing. The historical comparison used one pair per arm.
- **Fresh engine prefill:** engine-reported newly processed prompt tokens divided by engine prompt time, with zero reported prefix reuse. Do not substitute total prompt tokens for newly processed tokens on a cached request.
- **Request wall time:** elapsed time for the complete response. It includes generation and is not an isolated cache-restore or prefill timing.

The historical prefill workload used repetitive synthetic records at 128/512/2048 rows, approximately 2.1k/8.6k/35.8k Qwen tokens. Token counts differ across tokenizers. Compare TTFT for the same text when discussing different model families, and preserve the token counts alongside tokens/s. Performance on repetitive records does not predict the same rate on varied system prompts, tool schemas or documents.

## What can be reproduced here

`scripts/benchmark_prefill.py` provides the shareable synthetic prompt shape and client measurements. It requires an independently prepared engine, tokenizer, weights and serving template. It does not reproduce the original private quality suite or certify numerical parity between engines. No historical results are generated by this script during repository setup.

The curated JSON results can be checked against their own accounting, recorded digests and report tables with `scripts/validate.py`. If the local evidence archive is available, `scripts/import_local_summary.py` regenerates the selected aggregate fields. Source-file digests identify the private records used for extraction; they are not hashes of the published summaries or parameter references.

## Remaining limits

The original private fixtures and request traces are not released. Some contain real session prompt/memory material. A public quality-suite release requires reviewed fixtures, graders and request templates. Sanitizing the fixture text changes the workload and requires new suite hashes and a rerun; the original scores must not be assigned to it.

The Q8 checkpoint checks establish shared n-gram payload identity, conversion-source provenance and sampled GGUF parity, not complete expert numerical parity. Some source/build metadata remains incomplete, including a Strata source revision in the Q8 campaign pin file. The report marks these limits rather than inventing missing pins.

The cache sweep did not retain usable per-request cache-counter snapshots in its result JSON. Its live counter observations and extrapolated disk-budget recommendation are labeled accordingly. The incomplete live-tool chase produced zero graded trials and contributes no new quality result.
