# V100 benchmark report: Lapilli, Strata and sFNX configurations (November 24–26, 2026)

Published companion files: [curated results](../../results/2026-11-26/summary.json), [parameter references](../../configs/2026-11-25/parameters.json), and [methodology](../methodology.md). Historical directory names below identify records in the private evidence archive, not files distributed in this repository.

This report compares complete serving configurations, including MTP and DFlash2 variants. It does not isolate speculation as the cause of quality or formatting differences. The Q4_K_XL/Q8 Engram comparison in §3 is the closest model-payload match; templates, arithmetic, placement and scheduling still differ.

## Test platform

All campaigns ran on one machine:

- Ryzen 9 7945HX3D, 96 GiB installed RAM; approximately 93.5 GiB visible to Linux after iGPU and other system reservations
- Two Tesla V100 32 GB cards, both physical PCIe cards, each on a Gen3 x8 link (`nvidia-smi` link width and the per-arm hardware samples agree). The second card runs cross-flashed SXM2 VBIOS, so `nvidia-smi` reports it as "Tesla V100-SXM2-32GB" and exposes the SXM2 power-cap range (150–300 W, default 300 W) instead of the PCIe card's fixed 250 W; its identifying name is a VBIOS artifact, not a different module. `CUDA_DEVICE_ORDER=PCI_BUS_ID`, no thermal throttling observed during arms. Both cards ran at their VBIOS default power limits throughout the campaigns: 250 W (stock PCIe VBIOS) and 300 W (SXM2 VBIOS)
- Peer-to-peer access between the cards was enabled throughout: the AMD IOMMU is off (`amd_iommu=off`), and the same peer-verification program ran as a pre-arm gate in the campaigns — patterned correctness on the copy engine and SM remote read/write from 16 B to 64 MiB in both directions, all passing, with no kernel DMA or Xid errors. A dedicated October diagnostic on this host measured about 6.5–6.6 GB/s per direction and about 1.6 µs GPU-event peer-write latency with peer access enabled. These engines move expert reads across the PCIe peer path, so link width and peer state are part of every timing comparison here
- NVMe storage on the system SSD and the separate model SSD. Placement varied by campaign: the DeepSeek packs were on the system WD_BLACK SN850X; the Q8 campaign used model-drive Lapilli/Strata assets and system-drive sFNX GGUF shards. Later cache tests also used model-drive assets. Storage placement is a comparison limit, especially for disk-backed n-gram reads.
- GPU test arms ran separately from the production local-model controller. Transient-unit settings varied as listed below; `G` in these systemd settings denotes GiB.

| Campaign | Explicit memory settings in launch script | Explicit memlock setting |
|---|---|---|
| Initial Lapilli MTP8/MTP4 trials | `MemoryMax=80G MemorySwapMax=0`; no explicit `MemoryHigh` | Not explicitly set by the launcher |
| sFNX DFlash2/MTP8, Q8 three-engine comparison, prefill retest and Lapilli cache sweep | `MemoryHigh=82G MemoryMax=86G MemorySwapMax=0` | `LimitMEMLOCK=infinity` |
| Lapilli DeepSeek ISTA/Nace | `MemoryHigh=78G MemoryMax=82G MemorySwapMax=0` | `LimitMEMLOCK=infinity` |

Production stop/restore records are retained where present. The cache-test summaries also record controller recovery work; successful benchmark completion should not be read as proof that every campaign immediately restored production. These historical launch settings are separate from subsequent production-service changes.

## The frozen suite

Full-quality arms use the same task groups and trial counts, with suite and implementation hashes recorded per campaign. Family-specific sampling and native tool protocols differ. A matching trial count does not establish identical rendered prompts or numerical execution.

- 974 executed / 966 graded per arm (8 observation-only)
- Groups: local tasks (400, thinking + nonthinking), HumanEval (328), long-context retrieval (6), concurrency (16), XML tool-protocol suite (224 executed / 216 graded)
- Capped outputs stay failures; parser/protocol failures are not regraded. No scores were adjusted in any campaign.

One caution that applies to every table below: the tools group includes engine parser/integration failures, so it mixes model quality with serving-layer fidelity. Read it separately from the reasoning groups.

Counts include repeated tasks across modes, seeds and concurrency settings; 966 graded trials are not 966 independent questions. Full quality suites were not repeatedly rerun to estimate run-to-run variance. Small score differences below are descriptive, not evidence of statistical equivalence or an intrinsic speculation-quality effect.

## 1. Qwen3.8-Flash-Next serving configurations, November 24–25

The same model family was served by three engines: Lapilli (Basalt port, MTP speculation), sFNX (MTP8 and DFlash2 arms), and Strata (DFlash2, the captured production baseline). Target quantization, n-gram representation and drafter configuration differ. Lapilli ran the full suite; the sFNX arms followed the next day.

### Speed

Rates below use two distinct metrics. Solo decode is `(completion_tokens − 1) / (last streamed token time − first streamed token time)`, averaged across two runs per workload. Two-client aggregate throughput is the combined completion-token count of concurrent `code1` and `prose2` requests divided by total wall time, including queueing and prefill. It is not pure decode throughput and has one concurrent workload pair per arm.

Fresh prefill is the engine-reported rate on a new prompt with zero prefix reuse; TTFT is measured at the streaming client. The 2048-row workload is approximately 35.8k Qwen tokens. Its repetitive record text is a synthetic workload, not a promise of the same rate on varied agent prompts.

| Arm | Two-client aggregate (tok/s) | edit1 decode (tok/s) | code1 decode (tok/s) | prose2 decode (tok/s) | Fresh prefill (2048 rows) |
|---|---|---|---|---|---|
| Lapilli MTP8 | 101.5 | **149.6** | **118.3** | 79.5 | 1450 tok/s (TTFT 24.8 s) |
| Lapilli MTP4 | **105.4** | 141.6 | 109.6 | 78.6 | 1445 tok/s (TTFT 24.9 s) |
| sFNX MTP8 | 87.7 | 111.5 | 102.5 | **95.3** | **2058 tok/s** (TTFT 17.5 s) |
| sFNX DFlash2 | 84.7 | 106.4 | 100.4 | 82.5 | 2020 tok/s (TTFT 17.8 s) |
| Strata (Nov 24 refresh, production configuration) | 76.2 | 85.2 | 93.3 | 67.2 | 654 tok/s (TTFT 54.9 s) |

The refreshed Strata speed configuration here differs from the Strata Q4 control in §3. Its saved quality baseline also differs in date and draft confidence: the recorded quality arm used draft confidence 0, while the captured production setting was 0.35.

Recorded interpretation of these runs: Strata has the highest aggregate score; Lapilli leads edit/new-code decode; sFNX leads fresh prefill and prose decode. Matching "MTP8" across engines does not match effective draft lengths, scheduler, or drafter quantization — sFNX has a shared 16-row verification window, so two lanes cannot both use eight drafts plus first target rows, and adaptive proposal scheduling makes spec8 a limit, not a promise.

## 5. Prefill and conversation cache (November 26)

Evidence: `2026-11-26-prefill-cache-retest/RESULTS.json`, `2026-11-26-lapilli-cache-sweep/RESULTS.json`.

The retest separates fresh prompts from continuation turns. It does not determine a default model by itself.

- Fresh-prompt requests used cache budgets of 0 / 8 / 24 GiB. At the middle tier, the 0 and 8 GiB arms both processed 21,968 prompt tokens; mean request wall times were 14.07 and 14.60 s (a 3.8% difference). The 24 GiB arm processed 22,481 tokens in 14.85 s. These wall times include generation, and prompt sizes differ slightly for the 24 GiB arm; the data do not support a universal "within 3%" claim. They show no consistent fresh-prompt speed benefit from a larger conversation-cache budget. Fresh prompts had zero prefix reuse, so conversation-prefix reuse does not explain the earlier prefill advantage over Strata.
- Continuation requests (6-turn, ~35k-token growing conversation): 0 and 24 GiB arms completed warm turns in approximately 0.9–1.2 s with nearly all prompt tokens reused. The 8 GiB arm took 57.55 and 110.48 s on turns 5–6. The recorded peak was 82.2 GiB against `MemoryHigh=82G`, consistent with memory-pressure throttling. Treat those samples as pressure-contaminated, not an isolated measurement of cache overhead; no matched limit-change rerun was performed.
- Correction recorded during the retest: the cache budget is **not preallocated** — it is an LRU byte ceiling; a larger budget costs memory only as conversations actually park.

**Lapilli cache sweep** (RAM 4/8/16 GiB + disk 8 GiB tiers, 6 conversations x 3 turns @ ~33k tokens, plus engine-restart disk-tier test):

- Mean warm-turn wall times were 8.16 / 8.19 / 8.37 s for 4 / 8 / 16 GiB RAM budgets. Each restart test resent two distinct primed conversations: the first request took approximately 21 s and the second less than 1 s, with 33,010 of 33,017 tokens reported cached for both. These are request wall times, not isolated disk-read or restore timings; they do not prove a subsecond restore for every conversation.
- The summary records a live counter observation of 3 parked conversations, 3.4 GiB held and 2 evictions at a 4 GiB budget, versus 6 parked, 6.79 GiB held and no evictions at 16 GiB. However, the saved per-request `cache` objects in `lapilli-cache-sweep.json` are empty. Those live observations lack a corresponding raw counter snapshot in that file and need one before being treated as independently auditable eviction measurements.
- The disk-cache banner was enabled, files were written, and post-restart responses reported prefix reuse. The summary counted 61–100 files occupying approximately 4.2–6.9 GiB. A roughly 70 MiB file is not necessarily one retained conversation: multiple files or checkpoints can belong to one history. Dividing 8 GiB by 70 MiB gives approximately 117 files, not a validated conversation capacity. The earlier "60 conversations" estimate is withdrawn.
- The sweep proposed **16 GiB RAM / 32 GiB disk** as a conservative deployment choice. Only an **8 GiB disk budget** was tested; 32 GiB is an extrapolation, and this workload does not establish that 16 GiB is the minimum sufficient RAM budget or the fastest setting. A mixed-length sweep with saved eviction/restore counters and more histories is needed.
- The measured **cgroup `MemoryPeak`** was 51.1 / 50.1 / 50.1 GiB for the three arms. These are whole-unit peaks, not process RSS. The sFNX retest reported a 75.2 GiB peak with cache disabled. Memory headroom must be evaluated against the applicable campaign or deployment limits, rather than inferred from the configured cache ceiling alone.

## 6. Tool-protocol fidelity (November 26)

Evidence: `2026-11-26-tool-protocol-investigation/`, `2026-11-26-live-tool-chase/HANDOFF.json`.

- Offline replay isolated one parser defect: literal XML tool markup **inside a quoted JSON string was incorrectly extracted as an executable tool call**, altering otherwise valid requested JSON. The observed counterexample reproduced through all three Flash-Next serving parsers. This explains a subset of failures, not the full 150–190/216 score range or all cross-model differences.
- **sFNX serving fix (candidate-qualified):** a frontend-only patch keeps tool-like XML inside quoted JSON values as literal text while preserving genuine top-level tool calls. The original CPU gate passed 632 tests and 6,892 subtests, with four skipped tests subsequently rerun successfully (636 tests exercised in total; 32 new regression tests). Raw replay covered 216 trials and 351 responses: 8 responses changed, **no previously-passing responses changed**, and 702 chunk-invariance checks passed. The native binary and weights were unchanged. Targeted native-API qualification passed 32/32 cases; the full benchmark was not rerun with the fix, and original strict scores remain unchanged. Repairing a saved response does not establish success on unobserved later workflow turns.
- **Live chase (unresolved):** the archived production Strata IQ4_XS result is 150/216. Case/tool/template/sampling checks found agreement between the compared harnesses, but that alone does not rule out every harness or runtime effect. The attempted live repeat failed when the instrumented wrapper lost request-correlated raw text (`AssertionError: Missing request-correlated native raw text`), and graded zero trials. It is not a live reproduction of 150/216 and does not establish a checkpoint-only cause for the score gap.

The tool suite is primarily an XML protocol stress/regression suite, not a general agentic-capability score. Flash-Next uses XML-like native tool delimiters, while DeepSeek uses DSML, so XML adversarial payloads do not collide with the two family protocols in the same way. Model generation, serving extraction, API serialization and final-format failures must be reported separately. Neither the replay nor the scores establish MTP as the cause of a formatting failure.

## Conclusions

1. **The Q8 three-engine comparison has a six-pass spread across 966 graded trials** (Strata 864, Lapilli 860, sFNX 858). This is a descriptive result from one sampled suite, not proof of equivalence or an intrinsic MTP-versus-DFlash2 quality difference.
2. **The measured speed ordering favors different workloads:** Lapilli leads solo edit/new-code decode (~146–150 tok/s on `edit1` with spec8) and the tested two-client end-to-end aggregate; sFNX leads fresh synthetic prefill (~2.0k tok/s at 35.8k tokens) and solo prose decode. Two solo repeats and one concurrent pair per arm do not establish a stable performance guarantee for arbitrary agent workloads.
3. **Tool scores combine generation and serving fidelity.** A frontend fix corrected one literal-extraction defect in eight saved responses without changing previously-passing responses. It did not produce a new full-suite score; remaining failure categories still need separate diagnosis.
4. **Configuration differences limit causal claims.** The Q8 run improves model-payload comparability, but expert packing, templates, engine arithmetic, placement, drafter and cache policies remain different. No draft-disabled, otherwise matched reference isolates speculation effects in these campaigns.
5. **Within the tested DeepSeek configurations,** Nace leads aggregate/nonthinking/tool pass counts, while ISTA leads thinking-only pass counts and measured throughput. Family-specific protocols and sampling prevent reading the cross-family tool ranking as a general quality ranking.
6. **The cache results describe tested workloads, not a universal deployment optimum.** Retain the original grades and report pressure-contaminated timings, untested disk-budget extrapolations and incomplete counter capture explicitly. These runs alone do not select a default for every user's interactive workflow.

### Sampling, request budgets and workloads

The Flash-Next Q8 campaign used positive-temperature sampling:

| Mode | Temperature | top-p | top-k | min-p | Presence penalty | Frequency penalty | Repetition penalty | Maximum completion tokens |
|---|---|---|---|---|---|---|---|---|
| Nonthinking | 0.7 | 0.8 | 20 | 0 | 1.5 | 0 | 1 | 4096 |
| Thinking | 1.0 | 0.95 | 20 | 0 | 0 | 0 | 1 | 8192 |

The full-task requests set `enable_thinking` by mode, request medium reasoning effort and preserve prior thinking. Local tasks used seeds `20261105` and `20261106`; HumanEval and long-context used `20261105`; concurrency used `20261115`; XML protocol trials used `20261107` and `20261108`. Seeds are not a guarantee of matching random-number consumption across engines. Each engine exposed two slots with a 262,144-token context limit. DeepSeek instead used temperature 1.0, top-p 1.0, top-k 0, no presence/frequency penalty, repetition penalty 1.0 and reasoning effort 50, as recorded in its own settings.

The Q8 cache policies were not identical: Lapilli had a 4 GiB conversation RAM budget and an 8 GiB disk budget; sFNX had conversation caching disabled; Strata had a 24 GiB conversation RAM budget. Fresh-prefill samples had zero reported prefix reuse, but the configured budgets must still be preserved when reproducing memory usage or continuation behavior.

Speed tests used the `edit1`, `code1` and `prose2` user-task text from the sFNX reference fixtures, sent through each engine's served template. Solo decode tests ran twice per workload with a 1024-token completion cap and seeds `20261108` / `20261109`. The concurrent pair combined `code1` and `prose2`, used seed `20261110`, and ran once per arm.
